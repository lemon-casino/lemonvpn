macOS 桌面版补齐 Windows 版已有的应用级能力：系统代理、开机自启、单实例、RSS 统计、mihomo 兼容内核分发与 TUN 服务（实现见文末）。按端口找拥有进程的归属识别与 TUN 服务仍未实现：进程条件规则在 macOS 上不参与匹配，RSS/内存页只显示进程与系统总量。内核派发场景下引擎曾因 `compat::available()` 把内核的 TUN 能力上报为可用（macOS 的 utun 创建需要 root，应用以普通权限运行，实际不可用），`tun::supported()` 已改为按平台原生 TUN 支持判定（windows 与 macos 为真），侧栏 TUN 快捷开关按 capabilities 显隐。

系统代理沿用 Windows 的语义。接管前把每个网络服务（`networksetup -listallnetworkservices`，跳过停用服务）的 HTTP/HTTPS/SOCKS 与旁路域名快照写入数据目录 `system-proxy.json`，先落盘再改系统设置，任何部分生效都可被陈旧恢复找回；禁用时只恢复仍指向本引擎端口的服务，用户自行修改过的服务保持用户选择；记录的归属进程退出且回环端口无监听时才做陈旧恢复。重启换端口时保留最初快照，不重复备份。

单实例在 POSIX 上复用 `desktop.lock` 并以 `flock` 加锁：文件随进程崩溃自动释放，残留 PID 文本不阻止下次启动；`LEMONVPN_DATA_DIR` 缺省目录为 `~/Library/Application Support/LemonVPN`。开机自启写入 `~/Library/LaunchAgents/org.lemonvpn.desktop.plist`（RunAtLoad，程序参数含 `--autostart`），登录后启动，无需管理员；回读的 ProgramArguments 与当前程序一致才视为已开启。RSS 通过 mach `task_info(MACH_TASK_BASIC_INFO)` 读取，系统总量经 `sysctl hw.memsize`；可用内存暂不报告。sidecar 以 `getppid` 每 2 秒轮询实现等价于 Windows 父进程句柄的看门狗，父进程消失时按端口归属恢复代理并退出；内核 `lemonvpn-kernel` 以独立进程组启动，拥有者 Drop 时 `killpg` 一并回收。

内核按目标 triple 分发：amd64 使用最宽兼容的 `compatible` 构建、arm64 使用标准构建，均为 gzip 单文件，下载后 SHA256 与 `pins.env`（`MIHOMO_DARWIN_AMD64/ARM64_ASSET_SHA256`）核对，解压为 `lemonvpn-kernel` 并置 0o755；macOS 不走特权安装器，内容哈希另写入 `assets/mihomo-darwin.sha256` 随应用分发，由 TUN 服务安装内核前校验。`tauri.macos.conf.json` 把内核与 geodata 放进 `Contents/Resources`，引擎按 exe 同目录、`resources/`、`../Resources` 顺序查找；开发模式则由 prepare 脚本把内核放到 sidecar 旁。doona 桌面设置卡片对 macOS 显示自启开关，标题与文案按平台区分（macOS 显示"macOS 集成"，新增 `desktop.integrationMacos`/`desktop.autostartHelpMacos` 三语言键，Windows 文案不变）；侧栏 TUN 快捷开关改按 capabilities 的 `tun.available` 显隐，与设置页 TUN 卡同规则，避免在未实现平台点出错误。TUN 设置卡服务安装块从 Windows 专属扩到 windows||macos，改动通过重生成 `doona-lemonvpn-desktop.patch` 保留（`git -C doona diff HEAD --binary`，缺 `--binary` 会丢掉品牌图标等二进制改动）。

验证与边界：`lemonvpn-engine-platform` 对 `x86_64-apple-darwin` 与 `aarch64-apple-darwin` 编译检查通过（含 system_proxy 纯函数单测）；Windows 宿主壳层 12 项测试与 node 脚本 7 项测试通过；darwin 内核准备脚本端到端冒烟（缓存命中→gunzip→SHA256→manifest→许可证）。壳层（Tauri app）的 darwin 编译检查因 `objc2-exception-helper` 等需要原生 macOS SDK 的依赖无法在 Windows 上交叉完成，也未接 macOS CI 任务，需真机或后续 CI 验证；壳层 darwin 编译与打包已于 2026-11-08 在 macOS 虚拟机补验（见下）。engine-core 的 5 个单测失败（config/events/flows/probes/share）在本次改动前的 HEAD 上同样失败，属遗留问题，与 macOS 变更无关。签名、公证与 `universal-apple-darwin` 合并仍延后。

构建与冒烟（2026-11-08，macOS 15.2 x86_64 虚拟机，用户级 Node/pnpm/Rust 工具链）：完整 `pnpm --dir app build` 通过，产出 `LemonVPN.app` 与 `LemonVPN_0.1.30_x64.dmg`（版本号沿用 0.1.30，0.1.31 为下一发布预留）；虚拟机网络访问 GitHub CDN 不稳定，mihomo 内核、geodata 与许可证缓存按 pins.env SHA256 预种后命中。VM 中 Finder 的 AppleScript 布局步骤必然超时（-1712），DMG 由手动执行 `bundle_dmg.sh --skip-jenkins` 压制：镜像完整可用，但无自定义图标布局；staging 目录不放 Applications 链接（脚本自建），目标 DMG 先删除（convert 不覆盖）。首跑发现 sidecar 启动即 SIGBUS：`memory.rs` 曾把 `mach_task_self_` 声明为函数调用，而 macOS 导出的是数据符号（`mach_port_t`），调用即跳入只读数据段；改为 `extern static` 后修复。冒烟以临时端口 18084 与临时 `HOME` 数据目录进行（不设 `LEMONVPN_PARENT_PID`，未触碰真实系统代理与自启状态）：进程持续存活，`/health`、`/api/v1/capabilities`、`/api/v1/tun` 均 200，capabilities 报 `tun.available:false` 且 `runtime_memory` 广播 `process.rss_bytes`，`/api/v1/tun` 返回 `{"enabled":false,"supported":false}`；验证后已清理进程与临时目录。.app/.dmg/sidecar 已取回 Windows 工作区 `output/macos/`，SHA256 与 mac 端逐一核对一致。签名与公证仍延后。

macOS TUN 服务镜像 Windows 的特权服务架构：`lemonvpn-service` 由 engine-platform `[[bin]]` 在 darwin 同样编出并打进 `Contents/Resources`，安装经 UI 主动授权（osascript `with administrator privileges`，120 秒超时）后注册 LaunchDaemon `org.lemonvpn.tun`；服务目录 `/Library/Application Support/LemonVPN/Service/` 为 0755 root:wheel（二进制 0755、plist 0644），UDS `/var/run/lemonvpn-tun.sock` 0666 并以 getpeereid 校验连接方属主、以 LOCAL_PEERPID 轮询看门狗（250ms）确认引擎存活；协议为 4 字节小端长度前缀 JSON（128KiB 上限），action 含 start/process_rules/flush_dns/stop/status，单会话 Mutex，pid 不同拒绝接管。服务代跑内核：私有 runtime 目录、随机 secret、TUN fake-ip 198.18.0.1/16、external-controller 随机端口；流量链路为 utun→服务内核 TUN inbound→socks5 回环桥→引擎 compat::connect→节点出站，引擎侧 connect_tcp/bind_udp 经 darwin.rs 设 IP_BOUND_IF/IPV6_BOUND_IF 走物理网卡，compat 内核 `interface-name` 由 darwin::uplink_name() 提供。实现踩过的四个坑：macOS `fs::copy` 走 fcopyfile 会继承源文件属主，服务目录与二进制统一 root_own() chown 0:0；全量接管后 fd 暴涨，darwin sidecar 启动时把 RLIMIT_NOFILE 提到 min(10240, 硬上限)；SIGTERM 硬杀留孤儿内核，信号处理只置停止标志、accept 改 nonblocking 轮询，启动时 `pkill -f "Service/lemonvpn-kernel"` 清残留；最关键的是 macOS 上 IP_BOUND_IF 绑定物理网卡的 TCP 不走普通 default 路由——utun 捕获路由存在后 bound_if 连接直接报 Network is unreachable（python 对照实验证实），解法为服务端 start 时装一条 `route add -net 0.0.0.0/0 -ifscope <if> <gw>` 克隆默认路由、会话 Drop 时删除，引擎侧每秒重探 uplink、网络消失报 NotConnected。

TUN 服务全链路冒烟（最终构建；不触碰真实系统代理与自启，`LEMONVPN_DATA_DIR`/`LEMONVPN_ENGINE_PORT` 临时值，服务安装经 sudo 等价授权）：启用后 utun4 198.18.0.1 携 9 条分片路由（0/2…128.0/1，默认路由留在 en0，SSH 不断），`curl https://ipinfo.io/ip` 经代理出口 38.64.60.143，apple.com 与 neverssl.com 均 200，DNS 劫持 example.com→fake-ip 198.18.0.16；disable 后路由清空、服务内核退出，重启用恢复；引擎被 pkill 后看门狗 250ms 内清会话清路由；SIGTERM 重装无孤儿内核；卸载 bootout 后 plist/目录/socket 全清。UI osascript 真机授权弹窗与 arm64 构建未验证，签名公证仍延后。
